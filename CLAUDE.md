# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

HomeRadar è un'estensione Chrome (MV3, WXT + React + TypeScript) per agenti immobiliari: su Immobiliare.it, Idealista.it e Subito.it riconosce gli annunci di privati, ne costruisce lo storico prezzi in locale e segnala i lead (anzianità ≥ soglia oppure ribassi). Conversazione e testi dell'interfaccia in italiano.

## Comandi

```bash
npm run dev          # Chrome con estensione in hot reload
npm run build        # build in .output/chrome-mv3
npm run zip          # zip per il pilota
npm run typecheck
npm test             # unit test (Vitest, jsdom + fake-indexeddb)
npx vitest run tests/unit/core/rules.test.ts   # un singolo file
npx vitest run -t "Alta"                        # test per nome
npm run test:e2e     # build + Playwright su pagine fixture locali
node scripts/generate-icons.mjs                 # rigenera public/icon/*.png da src/shared/logo.ts
npm --prefix worker test                        # test del Worker del pilota (runtime Workers + D1 locale)
npm --prefix worker run dev                     # Worker in locale su :8787 (vedi docs/pilot-reporting.md)
```

## Architettura

Flusso Immobiliare: `bridge (MAIN world) → content script (ISOLATED) → adapter.parsePayload → background → IndexedDB → side panel`.
Flusso Idealista: `content script (ISOLATED) → adapter.readDocument (DOM già mostrato) → background → …`, nessun bridge.
Flusso Subito: `bridge (MAIN world) → content script (ISOLATED) → adapter.parsePayload → background → …`, come Immobiliare (content script comune in `src/content/payload-script.ts`).

- `src/bridge/bridge.ts`: unico codice nel contesto della pagina, installato da `*-bridge.content.ts`. Inoltra `__NEXT_DATA__` e le risposte XHR/fetch del sito (Immobiliare `/api-next/search-list/listings/`, Subito `hades.subito.it/v1/search/items`) via `window.postMessage`. Non fa mai richieste proprie e non deve mai rompere quelle del sito.
- `src/adapters/immobiliare/`: funzioni pure. Gli schemi zod sono la **lista dei campi ammessi**: ciò che non è dichiarato (telefoni, nomi, descrizioni) viene scartato. `urls.ts` non importa zod perché è usato anche dal bridge.
- `src/adapters/idealista/`: funzioni pure sul DOM delle card (`article.item[data-element-id]`, `data-is-professional-ad`; esclusi gli annunci suggeriti `.geo-reach-card`). Nessuna data di pubblicazione: l'età si stima dall'ID (`DEFAULT_CALIBRATION.idealista` in `core/age.ts`, più i punti appresi dalla pagina "più recenti"). Non leggere mai `.professional-name` (nome del privato).
- `src/adapters/subito/`: funzioni pure su `__NEXT_DATA__` della ricerca (`initialState.items`, compresi `galleryList`/`boostedItems`, che hanno card in pagina) e sulle risposte di `hades.subito.it/v1/search/items` intercettate dal bridge (paginazione SPA; il cambio di categoria ricarica la pagina). Schemi zod come whitelist: di `advertiser` solo `company`/`type` (il sito espone nome e telefono). Solo `type.key === 's'` e macrocategoria Immobili `'6'` (`category.parentId` in `__NEXT_DATA__`, `category.macrocategory_id` nell'API). La data di Subito è quella di rinnovo: l'età si stima dall'ID (`DEFAULT_CALIBRATION.subito`, più i punti appresi dagli annunci rinnovati oggi). La scheda annuncio non viene letta.
- `src/adapters/types.ts`: `PortalAdapter` con modalità `parsePayload` (bridge) o `readDocument` (DOM), più `cardFor`/`badgeHost`/`cardIds` per i badge.
- Copertina: `src/core/cover.ts` (server immagini ammessi per portale; Subito vuole `?rule=`). Gli adapter leggono l'URL (Immobiliare `properties[0].photo.urls.small`, Idealista `picture.item-multimedia img[src]`, Subito `images[0].cdnBaseUrl`/`cdn_base_url`), `ListingRecord.coverUrl` è facoltativo e mai `null`, `LeadView.covers` ha l'ordine di ripiego del gruppo, `src/ui/sidepanel/Cover.tsx` la mostra (pigra, senza referrer, riquadro neutro se non si carica).
- `src/core/`: logica pura e testabile. `rules.ts` (priorità e badge), `age.ts` (stima età da ID), `service.ts` (`LeadService`, unico scrittore su Dexie; la pulizia automatica decide per immobile: un gruppo si cancella solo se tutti i suoi annunci sono vecchi e non lavorati), `router.ts` (dispatch dei messaggi), `export.ts`, `lead-filters.ts` (ricerca a testo e fascia di prezzo del pannello, applicate prima del raggruppamento per scheda), `market.ts` (mediana €/m² dei privati salvati per zona, ripiego sulla città, un annuncio per immobile; calcolata in `listLeads()`, mai salvata), `same-property.ts` (stesso immobile su portali diversi: stessa città, m² entro 5% o 3 m², prezzo entro 5%, locali uguali; un annuncio per portale e ogni coppia compatibile; prima, per portale, le catene di ripubblicazione (ID più alto, visto la prima volta più di 30 minuti dopo l'ultima del vecchio e creato non prima, stessi dati, prezzo da −20% a +5%; coppie transitive tolte, casi ambigui lasciati soli), e il confronto tra portali usa solo l'ultimo annuncio di ogni catena; i gruppi si calcolano a ogni lettura, si salvano solo le coppie separate dall'agente nella tabella `splits`, anche nel backup), `lead-groups.ts` (costruisce i `LeadView`: principale, sempre un annuncio vivo, `others` con gli annunci precedenti (`previous`), storico prezzi della catena, valutazione con `evaluateGroup`, stato del gruppo; stato e note restano per annuncio e si scrivono su tutto il gruppo; il badge delle card e il numero dei richiami seguono il gruppo), `recall.ts` (giorni di ricontatto salvati come mezzanotte locale; il numero sull'icona conta quelli di oggi o scaduti, allarme `recall` a mezzanotte). Lo schema Dexie è in `db.ts` con versioni incrementali: per cambiarlo aggiungi una `version(n+1)` con migrazione, non modificare quelle esistenti.
- Giro delle ricerche: `src/core/searches.ts` (una ricerca per comune e categoria dalla zona `Settings.searchArea`, di default solo le case; URL per portale in `src/adapters/<portale>/search-urls.ts`; Subito una sola ricerca `immobili` con `advt=0` (porta tutte le categorie, `mixedCategories`: si tengono solo quelle scelte; gli scartati contano comunque come visti per "non più visto"); slug in `src/core/comuni.ts`, eccezioni delle province in `PROVINCE_SLUGS`), `src/core/category.ts` (categoria dalla tipologia; mercato e stesso immobile solo dentro la categoria), `src/core/sweep.ts` (stato puro: alternanza dei portali, fine ricerca alla prima pagina con un'agenzia su Immobiliare/Idealista, tetti, esito), `src/core/missing.ts` ("non più visto" dopo `MISSING_SWEEPS` giri completi della sua ricerca), `src/background/sweep-runner.ts` (finestra ridotta a icona, una scheda, pause, timeout, stato in `storage.session`; parte solo da `startSweep`). I content script mandano `pageRead` dopo ogni pagina di ricerca (`ParseResult.page`; `src/content/page-problem.ts` per verifica DataDome e pagina inesistente); il router passa all'orchestratore `ingest` e `pageRead` con la scheda (`ctx.tabId`). Elenco comuni: `src/shared/comuni.json` da `scripts/generate-comuni.mjs` (file ISTAT). Esito in `meta.sweep`, contatori `sweep_*` nel report. `scripts/ritmo/`: estensione di prova per misurare un giro reale.
- Backup: `src/core/backup.ts` (formato del file con schema zod come lista dei campi ammessi, unione all'importazione: vince l'`updatedAt` più recente del lead, non si cancella mai nulla), `src/core/auto-backup.ts` (settimanale, rotazione su 4 file in `Download/HomeRadar/`), `src/background/file-saver.ts` + `src/entrypoints/offscreen/` (il service worker non crea URL `blob:`: lo fa il documento offscreen, poi `chrome.downloads`). L'esito del download non si attende nel worker, che Chrome spegne se resta aperta la finestra "Salva con nome": il backup è segnato "in corso" in `meta.backup` e lo chiude `settleAutoBackup`, chiamata dal listener `downloads.onChanged` registrato all'avvio del worker. Se cambi la forma di un record salvato, aggiorna anche gli schemi di `backup.ts`; un cambio incompatibile del file alza `BACKUP_FORMAT_VERSION`.
- Misura del pilota: `src/core/usage.ts` (contatori d'uso puri: giorni locali di navigazione e di pannello, passaggi di stato, richiami, note, export; un'azione su un gruppo conta una volta), `src/core/pilot-store.ts` (`meta.install`, `meta.usage`, `meta.reporting`, `meta.feedbackQueue`, fuori dal backup), `src/core/report.ts` (`buildReport` e `sanitizeError`: nel report mai dati degli annunci), `src/background/reporter.ts` (invio giornaliero con l'allarme `report` e all'avvio solo se da più di 20 ore non c'è stato un invio né un tentativo; coda dei feedback, che partono anche con l'invio statistiche spento). L'URL del Worker viene da `WXT_REPORT_URL` nel `.env` al momento della build (`src/shared/report-config.ts`; `wxt.config.ts` aggiunge il dominio ai permessi): senza, nessun invio. Lo schema del report sta in `src/shared/report-schema.ts`, copiato identico in `worker/src/schema.ts` (un test controlla che coincidano: se lo cambi, copia il file). Il Worker (`worker/`, pacchetto separato, escluso dal `tsconfig` della radice) accetta `/report` e `/feedback` solo con codici pilota attivi e serve `/admin` con Basic Auth (`ADMIN_PASSWORD`). Se cambi cosa contiene il report, aggiorna l'informativa e alza `ONBOARDING_VERSION`.
- `src/entrypoints/`: solo cablaggio WXT (background, content script per portale, side panel); la logica sta nei moduli sopra.
- Portali attivi: `Settings.enabledPortals`. Il controller chiede `portalState` (`getPortalState`: `'active' | 'off' | 'onboarding'`) prima di ogni lettura (spento: non legge e toglie i badge); il router scarta comunque `ingest`/`parseStatus` dei portali spenti. Il bridge resta installato (`document_start`, non può leggere le impostazioni) ma inoltra solo dentro la pagina.
- Informativa: `src/core/onboarding.ts` (`ONBOARDING_VERSION`), conferma in `meta.onboarding` (fuori dal backup). Finché manca, il router scarta `ingest`/`parseStatus` e `getPortalState` risponde `'onboarding'` (i content script mostrano l'avviso). Schermata in `src/ui/onboarding/`, montata nella pagina `src/entrypoints/onboarding/` (aperta all'installazione) e nel pannello. Se un punto nuovo cambia cosa viene salvato o come viene usato, aggiorna il testo, alza `ONBOARDING_VERSION` e aggiungi la voce in `ONBOARDING_CHANGES`.
- `src/content/`: badge sulle card (`li` con link `/annunci/{id}/`), `RouteWatcher` che mostra il banner "ricarica" se dopo un cambio rotta non arrivano dati.
- `src/ui/sidepanel/`: React; parla col background solo tramite `api.ts`.
- Tipi condivisi in `src/shared/types.ts`; messaggi in `src/shared/messages.ts`.

## Vincoli da rispettare

- Mai richieste HTTP dell'estensione verso le pagine e le API del portale (DataDome; rischio legale). Il pannello può mostrare la copertina dei lead salvati dai server delle immagini dei portali (`src/core/cover.ts`). Niente crawling: il giro delle ricerche parte solo dal clic dell'agente su «Cerca», naviga una scheda alla volta con pause e si ferma alla prima verifica. L'unica richiesta in uscita è il report del pilota verso `WXT_REPORT_URL`.
- Salvare solo annunci di privati; mai telefoni o nomi del venditore.
- Il repository è pubblico: le fixture vanno sempre passate da `scripts/sanitize-fixture.mjs`; i file grezzi stanno in `fixtures-raw/` (ignorata). Per Immobiliare e Subito il sanitizer tiene solo i campi elencati (`KEEP_REAL_ESTATE`/`KEEP_RESULT`, `ad()`): se l'adattatore legge un campo nuovo, aggiungilo lì e rigenera. `tests/unit/adapters/fixtures-privacy.test.ts` controlla tutte le fixture.
- Timestamp sempre in ms epoch UTC.
- Se un portale cambia struttura: aggiorna gli schemi (Immobiliare, `src/adapters/immobiliare/schemas.ts`; Subito, `src/adapters/subito/schemas.ts`) o i selettori (Idealista, `src/adapters/idealista/parse.ts`), ricattura le fixture (vedi `docs/smoke-test.md`), non modificare le fixture a mano.
